# Project Context

## Миссия и конечная цель

Создать обучаемого автономного игрового агента для Slither.io-подобной игры. Агент сначала учится в собственной воспроизводимой симуляции, затем его зрительное восприятие и принятие решений переносятся в интеграцию с официальной Slither.io через браузерное расширение.

Желаемый пользовательский сценарий:
1. Пользователь открывает официальную Slither.io в браузере.
2. Запускает расширение Slither AI и явно включает/останавливает агента.
3. Расширение получает доступное визуальное состояние игрового поля.
4. Vision pipeline преобразует изображение в структурированное наблюдение.
5. Обученная модель выбирает действие.
6. Если правила игры и разрешённые интерфейсы допускают автоматизированный ввод, интеграционный слой передаёт действие игре. Пользователь наблюдает за ходом игры и сохраняет полный контроль над запуском и остановкой.

**Это целевая архитектура, а не обещание совместимости или гарантированного результата.** До реализации автоматического ввода необходимо проверить актуальные правила Slither.io и технически разрешённые способы взаимодействия. Не обходить антибот-защиту, не использовать приватный протокол, скрытую инъекцию, маскировку автоматизации или anti-detection. Если автоматическое управление не допускается, реализовать read-only perception + Advisor mode с рекомендациями человеку. Не менять конечную цель молча: любые ограничения интеграции фиксировать явно.

## Границы проекта

- Автономное массовое обучение выполняется в собственной локальной среде.
- Официальная игра — целевая среда для последующего тестирования perception и, только при подтверждённой допустимости, управления через расширение.
- Расширение должно иметь явные Start/Stop controls, показывать состояние агента и не запускать игру/агента без действия пользователя.
- Не обходить антибот-защиту, CAPTCHA, rate limits или иные механизмы защиты; не реверс-инжинирить приватный протокол для автоматизации.
- Самообучение означает контролируемый цикл train → evaluate → compare → promote/rollback. Не означает самораспространение или бесконтрольную модификацию кода.

## Целевые уровни мастерства

1. L1 — ориентация, сбор еды, базовое управление.
2. L2 — избегание стен и собственного тела, устойчивое выживание.
3. L3 — прогноз опасности и краткосрочное планирование.
4. L4 — тактическое взаимодействие с ботами-соперниками.
5. L5 — стратегия на длинном горизонте.
6. L6 — адаптация к разнообразным противникам и сценариям.

Это цели, а не достигнутые свойства текущей реализации.

## Начальный стек

- Python 3.11+
- NumPy
- Gymnasium API
- Stable-Baselines3 PPO
- PyTorch (CUDA — опционально, проверять runtime)
- Pygame (визуализация локальной среды)
- TensorBoard
- Для будущего расширения: стандартные browser extension APIs и отдельный локальный inference bridge, если это потребуется и допустимо. Конкретный механизм пока не выбран.

## Архитектура

- Environment: симуляция, наблюдения, действия, награды, terminal conditions.
- Agent: политика PPO и последующие recurrent/иерархические политики.
- Training: воспроизводимые эксперименты, callbacks, checkpoints.
- Evaluation: отдельные seeds и фиксированные сценарии.
- Vision: распознавание головы, тела, еды, границ и угроз по изображению.
- Integration: адаптер наблюдений и действий между браузерным расширением и моделью; реализация зависит от подтверждённых разрешённых интерфейсов.
- Browser extension: пользовательский запуск/остановка, захват доступного визуального состояния, отображение диагностики и интеграция с моделью.
- Advisor: резервный режим рекомендаций человеку, если автоматический ввод недопустим.
- Dashboard/Storage: визуализация, конфиги, логи, метрики, модели и метаданные.

## MVP observation/action contract

Реализованный MVP использует 10 float32-признаков:
- cos/sin текущего курса;
- относительные к позиции головы координаты еды (x/y);
- расстояние до еды, нормализованное диагональю арены;
- нормализованные расстояния до четырёх стен (left/right/bottom/top);
- нормализованная целевая длина тела.

В этой первой версии ещё нет лучевых датчиков тела/препятствий и других змей. Не приписывать MVP эти возможности.

Действия дискретны и относительны к текущему курсу: поворот налево, прямо, направо. Это снижает размерность и упрощает старт PPO.

Будущая реальная игра может иметь другое представление наблюдений и частоту управления. Нельзя считать, что текущий 10-feature observation напрямую совместим с картинкой Slither.io: понадобится отдельный perception/adapter layer и проверка sim-to-real gap.

## Метрики

- средняя/медианная длительность эпизода;
- средняя длина змеи;
- собранная еда;
- частота столкновений и причина завершения;
- win/survival rate против классов scripted opponents;
- reward — диагностическая метрика, не единственный критерий качества;
- throughput обучения, latency inference и использование GPU — технические показатели;
- для внешней интеграции — частота корректного распознавания и задержка perception → action.

## Текущее состояние

Реализованы базовые документы, Python package, простая Gymnasium-среда SnakeEnv, CLI smoke/train/evaluate и pytest-тесты. Код ещё не прошёл runtime-валидацию в целевом Linux-окружении. PPO CLI не означает, что обучение уже проводилось. Browser extension, vision pipeline и онлайн-интеграция не реализованы.

Аппаратная информация из прошлых сессий (RTX 3050 Mobile, Intel i5-12450H, около 14.8 GiB RAM, NVMe около 477 GB, Ubuntu Server 26.04.1, Docker, NVIDIA Container Toolkit 1.20.1) устаревающая и должна быть перепроверена перед настройкой обучения.
